# Project OS Personal — optional independent AI Counterweight

**Deployment contract:** This connector uses the OpenAI Responses API over TLS to generate an **unsigned** semantic review. It is OFF by default and cannot advance the Council mission or waive Checker/owner approval.

## Security model and onboarding

The existing, exact mission remains `MISSION-20261026-BE0827D3BD`. The Council dispatcher, original prompt, Counterweight gate, G0, G1 and owner-release gates are unchanged.

The connector supports the official fixed endpoint `https://api.openai.com/v1/responses`; it does not accept arbitrary URLs. HTTPS uses certificate verification with redirects forbidden. The request uses `store: false`, no tools, and strict JSON output. The full original user request and charter are sensitive; they are transmitted to the provider **only after explicit configuration**:

- `POS_CW_AI_ENABLE=1` — an operator's intentional opt-in to externally process the request.
- `POS_CW_AI_MODEL=<provider-model-that-supports-Responses-and-structured-output>` — explicit model; **no default**. Confirm availability and price with the provider.
- `POS_CW_AI_API_KEY=<real-secret>` — owner-provisioned credential; never committed or displayed in logs or chat.

None of these credentials was present on Railway when this connector was written. This deployment must therefore report `DISABLED_PENDING_EXPLICIT_CONFIGURATION`. Do not create example secrets or enable calls silently. Configure through Railway secure service-variable controls with the owner's approval. API usage may incur provider charges.

The new entrypoint strips `POS_CW_*` and `OPENAI_API_KEY` from the environment of Council, Brain and notification child processes; only its own connector thread can read the opt-in credential. No network listener, unauthenticated HTTP upload endpoint or public file share is opened.

## Private evidence transfer

1. Reuse existing immutable `COUNTERWEIGHT_REVIEW_REQUEST.json`, created and hash-bound to the original instruction and completed integrity worker.
2. Once opt-in and credentials are valid, create `COUNTERWEIGHT_AI_CALL_CLAIM.json` once to prevent duplicate provider charges or automatic retries after crashes.
3. Send the exact request through the fixed HTTPS provider, with strict output schema, no tools and `store: false`.
4. Validate the response completion, model, provider-supplied response ID, structured findings, unresolved corrections and size.
5. Write the authenticated-transport result to the **private persistent mission volume** (mode 0600):
   - `COUNTERWEIGHT_AI_RAW_RESPONSE.json` — provider receipt for separate operator audit.
   - `COUNTERWEIGHT_EXTERNAL_EVIDENCE.json` — response ID, request hash, raw receipt hash, verdict hash, and `PENDING_SEPARATE_VERIFICATION`.
   - `COUNTERWEIGHT_REVIEW.json` — semantic findings and scope/risk analysis, **UNSIGNED**.
6. The existing semantic-review intake refuses to accept these files until a separate reviewer signature and distinct operator attestation are supplied and checked. Neither is generated by the connector. Do not self-sign model output or represent the model as a human operator.
7. Only the pre-existing dispatcher may process an accepted report; negative verdicts hold, positive Counterweight verification only advances to the Directors SPEC_PACKET stage. Checker and owner gates still operate normally.

### Failure behaviour

Missing opt-in or configuration produces a status only: no provider request. An HTTP error, invalid response or partial transfer produces a fail-closed hold; no automatic retry, no fabricated signature and no stage change. The persistent claim requires explicit manual reconciliation before any new billable call. On restart, an already-saved response may finish the same write-once transfer without another API request; any mismatch blocks the transfer.

Status events contain only the mission ID, request hash, provider response ID digest (not full contents), status and release flags. Never log API keys, raw prompts, full provider responses, HMACs, or reviewer evidence.

### Boundaries and limitations

An HTTPS response and its locally hashed receipt are auditable, but they are **not cryptographically attested by the provider**. They do not prove reviewer independence on their own. An authorised, distinct operator must compare the stored provider receipt with the source in a trusted channel and provide the existing separate attestation/signatures. HMAC key possession on a single compromised host is not strong organisational separation. Use separately held identities/signing keys and authenticated provider-side receipts for production trust.

No general public upload API or automated reviewer/attestor identities are configured. This implements the secure transport path **from an authorised provider to the private host** and stages evidence for later distinct attestation; it does not finish the end-to-end independent review without credentials and legitimate signing parties.

### Tests

The development mock-provider suite tested no-key/no-opt-in, successful response staging, restart idempotence, malformed/incomplete provider output, mismatched model, tampered claims and evidence, mandatory dual attestation, and owner gate invariants. Repository integration tests are in `tests/test_counterweight_ai_connector.py`; run `python -m unittest discover -s tests -p 'test_counterweight*integration.py'` for original semantic tests, or `python -m unittest discover -s tests -p 'test_counterweight_ai_connector.py'` to exercise the connector with the actual dispatcher.

Production acceptance also requires live Railway logs showing `PROJECT_OS_AI_HOST_STARTED`, `COUNTERWEIGHT_AI_STATUS=DISABLED_PENDING_EXPLICIT_CONFIGURATION`, `COUNTERWEIGHT_SEMANTIC_STATUS=PENDING_EXTERNAL_REVIEW`, intact mission stage, `owner_approval=false`, and `release_authorised=false`.
